# 实测记录

记录 2026-11-04 的一次完整验证：路由组和档位写法能不能被识别、7 个具名 agent 实际落在哪个模型上、说大白话会不会主动派、只读权限拦住了什么、遇到了哪些坑。

测试环境是一台装了 Claude Code 和 magpie 的机器，用的是真实的全局配置。下面写的都是当天实际跑出来、从 magpie 用量记录里核到的结果，不是预期行为。

## 路由组加档位的写法

想确认的第一步是：agent 文件里写 `group/glm-fast:high[1m]` 这种"组名 + 档位 + 上下文"的写法，Claude Code 认不认，magpie 会不会按档位发出去。

建了两个临时测试 agent，一个写 `group/glm-fast:high[1m]`，一个写 `group/minimax:medium[1m]`，各跑一次，然后看 magpie 的记录。第一个落在 glm-5.3-flash、high 档，第二个落在 MiniMax-M3.1-Flash、medium 档，两次状态都是 200。

又试了直接把组当主模型：`claude -p --model group/glm-main`。落在 glm-5.3，状态 200。

结论是这种写法可用，组名后面跟档位和上下文长度不影响解析，magpie 会按档位发请求。

## 7 个具名 agent 的落点

想确认的第二步是：按 frontmatter 写死的模型，每个 agent 是不是真的落在预期的地方。

逐个跑了一次，结果都对：explorer 落 MiniMax、medium 档；researcher 落 glm-5.3-flash；reviewer 落 glm-5.3-flash；writer 落 deepseek-flash；diagnoser 落 glm-5.3-flash；extractor 落 MiniMax、medium 档；verifier 落 Opus。七个全部状态 200。

这说明"调用时不传 model、让它按 frontmatter 走"这条路是通的，也说明把 `opus` 档指向 glm-main 之后，verifier 没有受影响——因为它用的是 `group/opus`，不走别名。

## 主动派用：不点名会派给谁

这是最关心的一项，因为整套配置的前提就是"主脑自己会派"。

在 Opus 主会话里发了四句不点名的大白话，没有提任何 agent 名字，也没有说"派给谁"。

第一句"这几个脚本干嘛的、怎么调用"，派给了 explorer。第二句"查某个开源项目最新版本号"，派给了 researcher，它用 `gh` 的官方接口查到了版本。第三句"我刚改了清理脚本，看看有没有问题"，派给了 reviewer——测试时在脚本里埋了三个问题：删除范围从 zip 扩大到全部文件、`rm -rf` 直接拼接文件名可以注入、命令行参数能传任意目录。三个都被找了出来。第四句"日志里一直报 503，查查原因"，派给了 diagnoser，它先问是哪台机器、哪个服务，没有直接去动真实服务。

四个会话的 Opus 部分加起来开销很低，主要在拆解和验收上，真正干活的调用都落在了便宜模型上。

verifier 全程没有被自动叫出来，符合"description 里写不主动使用"的设计。

## 只读权限实际拦住了什么

这一项验证 `disallowedTools` 有没有生效，以及"只读"的边界在哪。

researcher 这边：能看到 Skill 工具，也能看到 ego-browser、agent-reach 这类浏览器技能，需要时可以按需加载；知识库的上传和读写被屏蔽了，生图被屏蔽；知识库检索保留，因为调研要用。

diagnoser 这边：保留了 SSH 执行命令，排障必须用；SSH 上传和知识库上传被屏蔽。

Bash 在两边都开着，符合设计——这是规则约束不是硬限制，agent 正文里写了只跑只读命令，验收时按这个核。

## 发现的问题

第一个：抓取工具读到了旧版本号。用网页读取工具抓 GitHub 的发布页，读到的是 0.2.15，官方接口给的是 0.2.19。网页缓存和接口不一致。已经在 researcher 的规则里加了一条：版本号、发布日期、star 数这类会变的数据优先走官方接口，两边不一致时以官方接口为准并注明。

第二个：没调用工具就标"已核实"。researcher 有一次在 0 次工具调用的情况下，把一条结论标成了已核实。已经改成：标已核实的唯一前提是本次任务里实际用工具读到了原文，没调用过工具就只能标未核实。

这两个问题都不是配置写错，是模型在省事，靠规则堵住。
