# 实测记录

记录两轮验证。2026-11-04 验证路由组和档位写法能不能被识别、7 个具名 agent 实际落在哪个模型上、说大白话会不会主动派、只读权限拦住了什么、遇到了哪些坑。2026-11-05 到 06 验证 Codex worker、WSL 派活、档位范围收口和组合切换。

测试环境是一台装了 Claude Code 和 magpie 的机器，用的是真实的全局配置。下面写的都是实际跑出来、从 magpie 用量记录里核到的结果，不是预期行为。

## 路由组加档位的写法

这一轮测的是当时的写法：agent 直接写档位组加档位。现在 agent 改写成角色组，档位由组合文件里的成员决定，但"组名后面跟档位能被识别"这条结论仍然成立。

想确认的第一步是：agent 文件里写 `group/glm-fast:high[1m]` 这种"组名 + 档位 + 上下文"的写法，Claude Code 认不认，magpie 会不会按档位发出去。

建了两个临时测试 agent，一个写 `group/glm-fast:high[1m]`，一个写 `group/minimax:medium[1m]`，各跑一次，然后看 magpie 的记录。第一个落在 glm-5.3-flash、high 档，第二个落在 MiniMax-M3.1-Flash、medium 档，两次状态都是 200。

又试了直接把组当主模型：`claude -p --model group/glm-main`。落在 glm-5.3，状态 200。

结论是这种写法可用，组名后面跟档位和上下文长度不影响解析，magpie 会按档位发请求。

## 7 个具名 agent 的落点

想确认的第二步是：按 frontmatter 写死的模型，每个 agent 是不是真的落在预期的地方。

逐个跑了一次，结果都对：explorer 落 MiniMax、medium 档；researcher 落 glm-5.3-flash；reviewer 落 glm-5.3-flash；writer 落 deepseek-flash；diagnoser 落 glm-5.3-flash；extractor 落 MiniMax、medium 档；verifier 落 Opus。七个全部状态 200。

这说明"调用时不传 model、让它按 frontmatter 走"这条路是通的，也说明把 `opus` 档指向 glm-main 之后，verifier 没有受影响——它当时用的是 `group/opus`，不走别名；现在 verifier 改用角色组 `verify`，同理。

## 主动派用：不点名会派给谁

这是最关心的一项，因为整套配置的前提就是"主脑自己会派"。

在 Opus 主会话里发了四句不点名的大白话，没有提任何 agent 名字，也没有说"派给谁"。

第一句"这几个脚本干嘛的、怎么调用"，派给了 explorer。第二句"查某个开源项目最新版本号"，派给了 researcher，它用 `gh` 的官方接口查到了版本。第三句"我刚改了清理脚本，看看有没有问题"，派给了 reviewer——测试时在脚本里埋了三个问题：删除范围从 zip 扩大到全部文件、`rm -rf` 直接拼接文件名可以注入、命令行参数能传任意目录。三个都被找了出来。第四句"日志里一直报 503，查查原因"，派给了 diagnoser，它先问是哪台机器、哪个服务，没有直接去动真实服务。

四个会话的 Opus 部分加起来开销很低，主要在拆解和验收上，真正干活的调用都落在了便宜模型上。

verifier 全程没有被自动叫出来，符合"description 里写不主动使用"的设计。

## 只读权限实际拦住了什么

这一项验证 `disallowedTools` 有没有生效，以及"只读"的边界在哪。

researcher 这边：能看到 Skill 工具，也能看到 ego-browser、agent-reach 这类浏览器技能，需要时可以按需加载；知识库的上传和读写被屏蔽了，生图被屏蔽；知识库检索保留，因为调研要用。

diagnoser 这边：保留了 SSH 执行命令，排障必须用；SSH 上传和知识库上传被屏蔽。

Bash 在两边都开着，符合设计——这是规则约束不是硬限制，agent 正文里写了只跑只读命令，验收时按这个核。

## 发现的问题

第一个：抓取工具读到了旧版本号。用网页读取工具抓 GitHub 的发布页，读到的是 0.2.15，官方接口给的是 0.2.19。网页缓存和接口不一致。已经在 researcher 的规则里加了一条：版本号、发布日期、star 数这类会变的数据优先走官方接口，两边不一致时以官方接口为准并注明。

第二个：没调用工具就标"已核实"。researcher 有一次在 0 次工具调用的情况下，把一条结论标成了已核实。已经改成：标已核实的唯一前提是本次任务里实际用工具读到了原文，没调用过工具就只能标未核实。

这两个问题都不是配置写错，是模型在省事，靠规则堵住。

## 推理档位：Orca worker 有效，原生子代理临时传无效

Orca worker 用 `--model group/glm-fast --effort low` 起了一个测试 worker，magpie 记录里它的请求落在 glm-5.3-flash、档位 low。所以 worker 的推理档位可以每次由主脑按任务难度决定。当时还没限制档位；现在只用 medium、high、xhigh 三档。

原生子代理则不行。派 explorer 时临时传 `effort: max`，派 reviewer 时传 `effort: low`，magpie 记录都是 high；explorer 文件里原本写的 medium 也被冲掉了。结论是原生子代理的档位只写在 agent 文件里，派的时候不传。

## Orca worker 看得见、关得掉、找得回

加了 `--keep-open` 的 worker 会在 Orca 对应工作区里开一个可见的 Claude Code 终端，干完不自动关，`worker-list` 显示终端处于保留状态。验收后用 `worker-release --dispatch <id>` 关闭，Orca 回执显示终端已关、对话记录已存档。关闭后用 `orca search` 按关键词能搜到这条会话，标题就是派活时写的 `--task-title`，所以标题要写成一眼能认出的中文。

## 2026-11-05 到 06：Codex、WSL、档位和组合

以下结论只针对这套测试环境，换环境需要重新核对。

### Codex 原生 worker

用 `--agent codex --model gpt-6.1-sol` 起 worker，能正常跑到完成。`--model` 写裸模型名，不带 `codex/` 前缀。Codex worker 不读 `~/.claude` 下的规则，任务说明里的固定规则要单独抄进去。

### WSL worker 跑通

通过 Orca 的 SSH 远程服务器把 worker 派进 WSL 的 ext4 检出，worker 正常完成。定向测试 31 通过、31 跳过，构建退出码 0；magpie 记录里这次请求落在 Codex sol。说明在该测试环境中 `--on <服务器名> --worktree "id:<repoId>::<路径>"` 这条路可用。

首次运行时 worker 报 `agent_prompt_blocked`。原因是 claude 在终端模式下弹了"要不要把 auto 设为默认权限模式"，没人回答就卡住了。在 `~/.claude.json` 里写入 `hasSeenAutoDefaultNudge` 后恢复正常，同步脚本已经包含这个键。

### 档位范围收口

给 impl-strong 传 max 之后，请求落到 astra 时是 xhigh。组里写了 `:medium+high+xhigh` 和 `levels=medium,high,xhigh`，范围外的档位会被换成最接近的一档，不会整轮跳过。

在该环境的测试里，改之前的坑是：Codex 成员没钉档位时，收到 max 请求会被 magpie 跳过，整轮落到兜底的 GLM。表现是请求成功，但干活的换成了便宜模型。

### stays=auto 的问题

该环境的示例 Codex 组合最初用 `stays=auto`。2026-11-05 夜里 chatgpt.com 经代理断连几次后，对话一直粘在兜底的 GLM 上，约七成请求落到了 GLM。改成 `stays=turn` 后，每轮新对话重新从第一顺位 Codex 选。切换前已经开始的对话可能还留在旧模型上，核对时要看切换后新开的对话。

## 从这两轮里能带走的经验

下面三条不依赖具体供应商，换环境也值得先检查。

第一，成员没钉支持范围内的档位、又收到网关不支持的档位请求时，请求可能被跳过，整轮落到组里的兜底成员，表面看还是成功。给成员写清支持的档位范围，并让组只接受这个范围，可以避免。

第二，路由先主后备、又用 `stays=auto` 时，主模型一次不可用会让对话粘在兜底模型上，后续请求可能大量落到兜底。需要每轮重新尝试主模型时，把 `stays` 设成 `turn`；是否这样做，取决于你更在意稳定还是更在意主模型的使用率。

第三，Orca 用终端模式首次启动 claude 时，可能停在交互提示上，worker 报 `agent_prompt_blocked`。先读终端输出确认是什么提示，再把对应的"已看过"标记预先写进配置，可以避免。

## 这次没覆盖到的

前一轮的空白还在：没有跑全所有技能和所有模型的组合，没有测 `claude -p` 在长任务下的稳定性，Orca 界面里重新打开已关闭会话那一步没有替用户点过。

新加的几项里，WSL 只测了单个 worker 跑测试和构建，多个 worker 同时构建或测试时的资源余量没有测过；Codex 额度耗尽后自动顺延到国产模型，只在小范围见过，没有专门做耗尽测试；组合切换后旧会话粘在哪个模型上，只做了抽样观察，没有逐个会话核对。这些留到后面补。
