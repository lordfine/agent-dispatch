# 设计决策

这份文档记录这套配置为什么长这样。每条尽量回答三个问题：当时要解决什么、为什么这么选、代价是什么。以后想改配置的人，先看这里再动手。

## 总原则：贵的只做判断

最初要解决的问题很直接：Opus 5.5 按次计费，长上下文更贵，而一次完整的开发任务里，大部分动作并不需要这个级别的判断力。读文件、找调用链、搜资料、跑测试、写初稿，这些活换成便宜模型结果差不了多少，差的是钱。

所以主会话被压到只剩四件事：拆解任务、做决策、验收结果、跟你沟通。其余全派出去。这条原则是所有后续决策的出发点，后面每一条都是它的推论或补救。

代价是主脑要额外承担"派活"的开销：写任务说明、看凭证、判断要不要返工。任务太小的时候这个开销比省下的还多，所以手册里明确写了：少量文件的小改动、看几张截图，主脑自己做反而更省。

## 为什么用具名 agent、把模型写死在 frontmatter

Claude Code 子代理的模型解析顺序是：调用时传的 `model` 参数 > frontmatter 里的 `model` > `CLAUDE_CODE_SUBAGENT_MODEL` 环境变量 > 主会话模型。

这个顺序意味着两件事。一是调用时传参数优先级最高，但只能传别名，传不了 magpie 的组名，所以靠"每次派活时指定模型"这条路既啰嗦又表达力不够。二是把模型写进 frontmatter，只要调用时不传参数，就一定按文件里的来，不受环境和主会话影响。

于是就有了现在的写法：7 个 agent 各有自己的文件，frontmatter 里写死 `model`，规则是调用时一律不传 `model`。这样同一个 agent 在 Opus 会话、GLM 会话、`claude -p` 里跑，落点都一样。

代价是换模型要改文件。但组的引入把这件事变成了改 magpie，见下面第三条。

## 同族陷阱：为什么禁用内置 Explore 和 Plan

踩过的坑是：在 Opus 主会话里传 `model="opus"`，解析出来的就是 Opus 本身，不是你以为的"另一个 Opus"。

内置 Explore 不指定模型，官方文档说它的模型由 Claude Code 按环境决定：经 `ANTHROPIC_BASE_URL` 网关（比如 magpie）时跑在 `opus` 别名指向的模型上，部分云平台上跟随主会话。总之它可能落到 Opus，而且不受你的 agent 文件控制，用起来既贵又没法保证。

这两件事叠加起来，看起来"我派了子代理应该省钱了"，实际上账单一点没少。所以规则定成：不用内置 Explore、Plan；`general-purpose` 不得已要用时只传 `sonnet` 或 `fable`（分别指向 glm-5.3 和 glm-5.3-flash），绝不传 `opus`。要摸底就派 explorer，它有独立的只读定义和自己的模型。

## 模型名统一写 magpie 路由组

最早的写法里直接写供应商的模型名。曾经遇到供应商改了模型 id，旧写法靠网关留下的改名记录还能用一阵；但换供应商时那些写死的名字不会跟着走，只能去所有 agent 文件里逐个改。

改成路由组之后，agent 文件里写的是 `group/glm-main`、`group/glm-fast` 这种组名，组名不带版本号。组成员在 magpie 里配，升级模型或换来源时改一条命令：`magpie group set glm-main models=<来源>/<新模型>`。agent、派活手册、Orca 启动命令都不用动。

组还有一个附带好处：`magpie groups` 一眼能看到每个组现在指向谁，出问题时排查范围小很多。

代价是多了一层间接，新装的人必须先把组建好，否则 agent 文件里引用的组不存在，子代理起不来。这也是使用指南里把建组单列成一步的原因。

## 描述写成触发场景加"主动使用"

Claude Code 官方文档说，主会话决定派给谁，看的是三样：请求内容、agent 的 description、当前上下文，并建议在 description 里写 use proactively 来鼓励主动派用。所以每个 agent 的 description 都不写"我是某某专家"，而是写"什么时候该派我"，并且带上"主动使用"。

verifier 反过来，description 里明确写"不主动使用"，只在用户点名、关键决策复核、高风险上线前验收、两个执行者结论冲突时才派。原因是它跑在 Opus 上，按次计费贵，一旦被自动叫出来就失去了省钱的意义。

这条设计直接决定了实测里"主动派用"能不能成：四个不点名的大白话全部派对了，靠的就是 description 写的是场景而不是身份。

## 只读靠 disallowedTools，但 Bash 是规则约束

子代理会继承主会话的权限模式和 MCP 工具。只读 agent 的做法是用 frontmatter 的 `disallowedTools` 屏蔽掉写操作：Edit、Write、NotebookEdit，以及几个 MCP 的写能力——知识库上传和改写、生图，还有 SSH：diagnoser 要远程取证，只屏蔽 SSH 上传，保留执行命令；其余 agent 整套 SSH 工具都屏蔽。检索类的 MCP 工具保留，因为调研和排障要用。extractor 例外地保留了 Write，因为抽取结果常常要落成文件，但它屏蔽了 Edit，不改已有文件，也屏蔽了上网工具。writer 同理保留写文件能力，只写任务指定的路径。

这里有个必须说清的边界：Bash 仍然开着。diagnoser 要跑日志、状态查询，explorer 要跑 `git log`，关掉 Bash 这些活就干不了。所以"只读"对 Bash 来说是一条写在 agent 正文里的规则约束，不是工具层面的硬限制。真正防住误写的，是规则加上主脑的验收。

同样，对外发消息这类走命令行的动作也没法从工具层面禁掉，只能靠规则。这条限制不要当成已经解决的问题。

## GLM 内容审核 1301 的处理

GLM 系列偶尔会把正常内容判成敏感，报错信息是"系统检测到输入或生成内容可能包含不安全或敏感内容"。麻烦的地方在于这个错误藏在 HTTP 200 的响应流里，网关看到的是一次成功请求，故障转移机制接不住，表现就是"没报错但没产出"。

最后定成人工规则：同一个 agent 换 MiniMax 重派一次，或者在回复里说明换过模型；长任务、准确性要求高的改成 Orca worker 指定 DeepSeek。涉及代理、封号、内容风控这类话题，一开始就用 MiniMax 或 DeepSeek，别等它被拦。

## 不让 MiniMax 做实现

MiniMax 在结果不好校验的时候会编：给一个它能对照的原文，抽取和转录质量不错；让它判断"外面有没有这条信息"或者写一段没人能立刻验对错的代码，就容易出看起来很像那么回事、实际上不对的东西。

所以分工上把它放在有原文可对照的位置：explorer 摸代码（结论带路径行号，能核）、extractor 转录（材料在手，能对照）、守望者（只发"继续"，不需要判断）。实现类明确不派给它，这一点和用户的实际偏好也一致。

## 和 mattpocock 技能怎么配合

那套技能里写的是"派一个子代理"，没指定类型。在 Opus 主会话下直接派，就落到 Opus 上，前面说的省钱全白费。

解决办法是在派活手册第 9 节写一张映射：code-review 的两个审查子 agent 都换成 reviewer；research 技能和 wayfinder 的调研票换成 researcher；架构走查和 implement-spec 的探索子代理换成 explorer；implement-spec 的实现者和合并者用 general-purpose 加 `model="fable"`，复杂票用 `"sonnet"`，隔离方式用 worktree；chief-of-staff 里的子代理按角色选具名 agent；claude-handoff 的后台 agent 用 general-purpose 加 `"sonnet"`。

实现类还有一条更彻底的做法：不在 Opus 会话里跑。开一个主模型是 glm-5.3 的实现会话跑 `/implement`、`/tdd`，票与票之间 `/clear`。这样实现阶段的每次调用都不经过 Opus，也就不存在"忘了映射"的风险。Opus 会话留给对话和决策类技能，以及 code-review 的结论验收。

代价是你要在两个会话之间来回切，上下文不共享。这个代价是明摆着的，接不接受取决于任务本身：需要来回讨论的需求留在 Opus 会话，照着规格实现的活放实现会话。

## 被放弃的方案

看过几个现成的多 agent 编排项目，都没用。

oh-my-openagent 没有 Claude Code 宿主，只能在自己的壳里跑，agent 定义和技能都用不上。claude-flow 和 Orca 功能重叠，社区口碑虚高，接进来反而多一层要维护的东西。dsh-superagent 还在原型阶段，稳定性不够。另外有一个 codex-claude-bridge，主控写死在 Codex 上，思路和本项目相反——它让 Codex 当主控，而我们要的是 Claude Code 当主控、Codex 最多当 worker，所以只在"相关项目"里提一句。

取舍的原则是：优先用现成轮子，其次二开，最后才自研。这套配置之所以是配置文件而不是一个程序，也是这个原则的结果——Claude Code 已经提供了子代理、技能、权限这些原语，够用了，没必要再造一层。

## 这套设计的已知代价

写在这里，免得后来的人以为它没有缺点。

主脑的派活开销是实打实的，任务粒度太细时不如自己干。只读对 Bash 不是硬约束，靠规则和验收兜底。GLM 的内容审核会随机打断流程，需要人工换模型。子代理不能追加指令，一次没说清就得重派。Orca 的 worktree 和 code-review 都依赖 git，非 git 目录用不了。这些都不是配置能解决的，属于这套方案的边界。
