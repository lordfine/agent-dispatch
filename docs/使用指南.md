# 使用指南

这份文档讲怎么把这套装起来、装完怎么用、遇到常见情况该怎么办。看完你应该能判断"我这句大白话会派给谁"，以及出了事去哪找原因。

## 这套东西装完是什么样

这一节说明装完你手上多了什么，以及哪些事它管不到。

装完之后，你的 Claude Code 多了 7 个可以直接点名的子代理、三个技能（日常派活的 `dispatch`、初始化和复盘的 `dispatch-retro`、写反馈的 `dispatch-feedback`），以及一份只属于你的个人配置 `~/.claude/派活配置/`。主会话还是 Opus 5.5 这类强模型，但它不再自己读十几个文件、自己搜网页，而是把这些活派出去，自己只留拆解、决策、验收和跟你说话。

`dispatch` 手册按渐进加载写：入口只放决策规则（派给谁、定什么档、规格写什么、怎么验收），Orca、WSL、测试、组合路由各写一篇参考，用到才读。没有 WSL 的人不会读到 WSL 那篇，省 token。

每个子代理的 model 写的是一个角色路由组，比如 `group/explore`、`group/review`。组里具体放谁，由个人配置里的在用组合决定。仓库给的两份示例里，一份放 GLM、MiniMax、DeepSeek，另一份放 Codex 的 Terra、Sol、Astra；成员可以按自己的需要替换。换组合就是换一整套干活的模型，agent 文件不用动。

它管不到的地方也说清楚：这是配置和规则，不改 Claude Code 本身的行为；模型的落点最终由 magpie 的角色组和组合决定；magpie 没开、组没建对或者组合文件里的来源没替换，子代理就可能起不来，或者落到不是你想要的地方。

## 安装

在仓库根目录跑 `python 安装.py`（先加 `--演练` 看要做什么），装完新开会话输入 `/dispatch-retro`，跟着引导生成个人配置。详细步骤、从 v2 升级、不用 magpie 时怎么改，看 [安装与自定义](安装与自定义.md)。

想只在某个项目里用，就把 agent 文件放到项目根的 `.claude/agents/`。项目级和全局同名时项目级优先，可以拿它给某个仓库单独换模型。

## 三种调用方式

这一节解决"我到底该敲斜杠还是说人话"。

第一种是 mattpocock 那套流程技能，比如 `/grill-with-docs`、`/to-spec`、`/to-tickets`、`/implement`、`/implement-spec`、`/wayfinder` 等二十来个。它们文件头写了 `disable-model-invocation: true`，只能你自己敲斜杠触发，模型不会自己叫出来。这是有意的：这些技能步骤重、会改文件，不适合被自动触发。

第二种是工具技能，比如 grilling、code-review、tdd、diagnosing-bugs、research、domain-modeling、codebase-design、prototype、resolving-merge-conflicts。说大白话有可能自动触发，但不确定，想确保跑到就敲斜杠。

第三种是 7 个具名 agent。它们默认是隐性的，你说大白话，Opus 自己判断派不派、派给谁；想指定这一次一定给它，就直接点名，或者用 `@"explorer (agent)"` 这种写法强制这一次派给 explorer。

这三种的区别值得记一下：技能是"一套流程"，agent 是"一个干活的角色"。技能里面如果要派子代理，比如 code-review 会派两个审查子代理，按派活手册 `参考/配合其他技能.md` 的映射换成 reviewer，不会落到 Opus 上。

## 常见说法对应什么行为

这一节用几个真实会说的话，帮你建立"我这么说，会发生什么"的直觉。

你说"这个项目我两周没碰了，看看做到哪了"，Opus 会派 explorer。它会先读项目根的 CLAUDE.md、AGENTS.md、README，再看 `git log --oneline -20` 和 `git status`，回来给你一份带文件路径和行号的结论清单，不超过 40 行。

你说"让 researcher 查一下 X 最新版有没有支持 Y，只要官方来源"，它会去查官方文档、仓库源码和官方接口，每条事实标已核实或未核实并附链接。版本号这类会变的数据它会走官方接口而不是网页，因为网页可能读到缓存。

你说"我刚改了 cleanup.py，看看有没有问题"，Opus 派 reviewer。审查结果每条带 `文件:行号`、触发条件和严重度，站不住的结论它自己会删掉。

你说"日志里一直报 503，查查原因"，派 diagnoser。它第一句会先问你哪台机器、哪个环境、哪个服务，没问清就停下来，不会跑到本机上去猜别的机器的问题。它只跑只读命令，交付是现象、证据、按可能性排序的原因、每个原因的验证命令、建议修法和回滚方案。

你说"把这几张截图里的数据整理成表"，派 extractor。它只处理你给的材料，材料里没有的字段写"原文未提及"，不补全也不润色。它不上网，所以别让它判断"外面有没有这条信息"。

你说"把这些定下来的结论写成一份交接文档"，派 writer。它只写你指定的路径，写完交回来验收，不往外发。

一个开发流程走下来是这样的：`/grill-with-docs` 拷问需求，`/to-spec` 出规格，`/to-tickets` 拆票；然后离开 Opus 会话，开一个主模型是实现档的会话（比如 `claude --model group/impl`），每张票跑 `/implement`，两张票之间 `/clear` 防止上下文越滚越长；回到 Opus 会话跑 `/code-review`，它并行派两个 reviewer，一个查编码规范、一个查需求符合度；合并和 push 之前会问你。

要并行时，你说"这两张票互不依赖，开两个 Orca worker 并行做"。Opus 会给每张票写一份自包含的任务说明，用独立 worktree 起 worker。并发上限写在个人配置里。worker 干完停在"改完未提交"，不会自己 commit。

## 实现类任务怎么派

这一节解决"要改代码的活交给谁、任务说明写到什么程度"。

子代理是只读设计的，改代码走两条路：Orca worker，或者你自己开一个实现会话。

Orca worker 分几种：清单式的确定性活（固定清单的断言对齐、文案、字段替换、已定位的小修）用 `group/impl-lite`；常规实现用 `group/impl`；复杂、跨模块、需要判断的用 `group/impl-strong`。这三个组只是分组定义，组里放什么模型你按额度在组合里定，第一顺位相同时 impl-strong 就等于 impl 加高推理档。还有一个守望者用 haiku 档，专门盯外部 agent 的会话，只发"继续"。想用 Codex 自己的工具链，可以起 Codex 原生 worker（`--agent codex`），它不读 `~/.claude` 下的规则，规格里的固定规则会原样带过去。命令和坑看手册 `参考/Orca.md`，先跑一次 `orca skills get orchestration` 读和当前版本匹配的指南。

派活前 Opus 先定风险档（小、中、大，决定流程轻重和要不要审查），再定推理档，只用三档：

- medium：固定清单的断言对齐、文案、字段替换。
- high：已定位、边界明确的修复与补测，拿不准时用它。
- xhigh：方案性工作、并发、异步恢复、外部结果未知、不可逆迁移；前端开放设计和视觉用 impl-strong 加 xhigh。

确定性的活可以降一档推理或改用 impl-lite，允许首次交付后按明确反馈补一轮；验收标准不随档位下降。资源紧时依次减并发、降推理档、换常规模型，最后才减审查。

任务说明照 `模板/规格.md` 写：开头四行是风险档、确定性、推理档、返工原因（派活记录要用）；正文写目标、基线、允许改和禁止碰的范围、已知现状、完成判据；中档、大档再写四栏（外部行为、改动接缝、测试决策、不做什么）。模板末尾是实现者固定规则，原样带上：不回退别人的改动、Bash 一次一条命令、bash 变量名只用英文、往 WSL 传变量先写成脚本、先写会失败的测试、停在改完未提交。

全量测试在集成前和发版前各跑一次；大档票和改全局语义的票交付前再跑一次。一台测试机同一时间只跑一个全量，用 `脚本/全量排队.sh` 排队，不靠各会话自觉，细节看 `参考/验收与测试.md`。

不开 Orca 也行。直接开一个主模型是实现档的会话，跑 `/implement`、`/tdd` 这类流程技能，每张票之间 `/clear`。

## 子代理和独立会话的区别

这一节解决"什么时候该派子代理、什么时候该另开会话"。

子代理是在当前会话里分出去的，有自己的上下文，干完把结果交回来就结束，你没法再给它追加指令。适合一次能说清、不需要来回追问的活。

独立会话是一个完整的 Claude Code 进程，有自己的主模型，你可以持续跟它对话、追加指令。Orca worker、手动开的实现会话、`claude -p` 都属于这一类。

有个容易搞混的点：Claude Code 的独立会话一样能用 `~/.claude/agents` 里的 agent，而 agent 用哪个模型只看它自己文件里写的，和谁派它无关。所以哪怕是在一个主模型是 GLM 的会话里，你点 reviewer，它还是跑在 `group/review` 上。至于 `group/review` 里是国产模型还是 Codex，看当前组合。

Codex 有两种接法，别混。用 `--agent claude --model group/impl` 时，起的是 Claude Code，只是模型由 magpie 路由到 Codex，这套 agent 文件和规则照常生效。用 `--agent codex` 时，起的是 Codex 自己的进程，它不读 `~/.claude` 下的任何规则，这套配置对它不生效。

## 新项目怎么开始

这一节给从零开始的项目一条最短路径。

先 `git init`。Orca 的独立 worktree 和 code-review 都依赖 git，没有 git 这两样都用不了。

然后跑 `/setup-matt-pocock-skills` 初始化技能产物。一个人用的话，推荐选本地 markdown 放在 `.scratch/` 里，省去配外部服务的麻烦。

之后走主流程：拷问、出规格、拆票、实现、审查。跑起来之后，项目根会慢慢长出自己的 CLAUDE.md 和规格文档，后面每次派活的质量都会跟着变好。

## 老项目怎么接手

这一节给已经有一堆代码、可能还没文档的仓库一个入口。

先派 explorer 摸底，让它读结构、找入口、看 git 历史，把现状写成带行号的清单。这一步很关键，后面所有判断都建立在它上面。

如果仓库里没有 CLAUDE.md 或 AGENTS.md，让 writer 根据 explorer 的结论起草一份，你看过再定稿。没有这份东西，子代理每次都得从零摸索。

是 git 仓库就把 mattpocock 技能初始化一下。要重构就用 `/improve-codebase-architecture`，出了 bug 就用 `/diagnosing-bugs`，它会派 diagnoser 只读取证。

如果目标目录不是 git 仓库，那就只能用原生子代理，Orca worktree 和 code-review 都用不了，这个限制绕不过去。

## 报错和改派

这一节解决"跑挂了怎么办"，重点是别盲目重试。

GLM 内容审核的 1301 是用 GLM 时最常见的。GLM 偶尔会把正常内容判成敏感，报错藏在 HTTP 200 的响应流里，网关的故障转移接不住，所以看起来像成功其实没产出。处理办法有两个：同一个 agent 用 `model="haiku"`（指向 MiniMax）重派一次，或者在回复里说一句"我换了个模型重派"；如果是长任务、对准确性要求高，改成 Orca worker 指定 `group/ds-flash`。遇到错误时先核实原因，再选择可用的替代模型。

503 No available accounts 和 429 是号池满或限流，等一会儿重派；连续失败就把模型降一档，例如把主力模型换成同来源更快的模型。

其他报错先看原文再决定，不要照着上一条的经验乱试。同一种方法连续失败两次，停下来查文档。

还有一条经验：MiniMax 只派结果能校验的活，比如有原文可对照、有路径可核的。它不知道的时候倾向于编，所以别让它判断"外面有没有这条信息"。实现类也不要派给它。

## 验收和 git 规则

这一节讲怎么判断一次派活算不算完成，以及什么时候能动 git。

worker 交付必须带凭证：改动范围（`git diff --stat`）、测试命令和通过数、实际用的模型、没解决的风险。主脑按凭证核对，只对缺口和矛盾的地方复查，不重跑全部。部分通过不算完成。不通过就把修正意见发回原 worker，主脑不自己上手改。

git 上的规矩是：mattpocock 那套流程可以在功能分支上本地 commit，因为 code-review 要拿提交点来比对改动范围；但不直接提交 main 或 master；push 和合并等你同意。Orca worker 始终停在改完未提交。

## 核对模型落点

这一节教你怎么确认钱花在了该花的地方。

跑 `magpie usage --csv --last 1h`，看 `requested_model`、`served_model`、`effort` 三列。requested 是你要求的角色组或档位组，served 是实际落到的模型，effort 是推理档位。三个都对上，说明配置生效了。

如果发现有活落到了 Opus 上，最常见的原因是用了内置 Explore、Plan 这类子代理。官方文档说，内置 Explore 的模型由 Claude Code 按环境决定：经 `ANTHROPIC_BASE_URL` 网关（比如 magpie）时跑在 `opus` 别名指向的模型上，部分云平台上则跟随主会话。总之它可能落到 Opus，而且不受你的 agent 文件控制，所以摸底用自带的 explorer 更便宜也更可控。另一个原因是 `general-purpose` 传了 `"opus"`，在主会话是 Opus 时那等于派给 Opus 自己。

如果 `requested_model` 是角色组，但 `served_model` 不是你期望的模型，先 `magpie groups` 看这个组里现在是谁，再看当前组合是不是你切的那个。

## 升级模型和换供应商

这一节解决"模型换代了要改哪里"。

角色组改组合文件：把 `组合/国产.txt` 或 `组合/Codex.txt` 里的模型名换掉，再跑一次切换脚本。比如 GLM 出了新版，就把 `glm-5.3` 改成 `glm-5.5`，然后切一次国产组合。agent 文件、派活手册、Orca 命令全都不用动。

档位组直接改成员：`magpie group set glm-main models=<来源>/<新模型名>`。

`<来源>` 是你 magpie 里的供应商 id，用 `magpie providers` 能看到。组名和成员名都别写版本号，版本号只出现在组成员的具体模型名里。

## 组合怎么切

这一节解决"什么时候切、切完怎么确认"。

组合就是"每个角色组里放谁"的一份清单。在用的组合放在个人配置的 `组合/` 下，`当前组合.txt` 记着现在用哪个；skill 里的 `组合/` 只放切换脚本和两份示例。国产示例用 GLM / MiniMax / DeepSeek，Codex 示例用 Terra、Sol、Astra；两份都只是参考写法。

角色组按"干什么"命名，agent 和 worker 用，一共十个；组合换的就是这些组里的成员。组合文件末尾的 `magpie claude` 行决定 Claude Code 的 fable、opus、sonnet、haiku、subagent 档位指向哪个组，示例按大小排：fable 最大，给复杂票；sonnet 给确定性的清单活；haiku 最小，给 Claude Code 自己的后台小活。

切换命令：

```text
# Windows
python "$HOME\.claude\skills\dispatch\组合\切换组合.py" Codex
# WSL
python3 ~/.claude/skills/dispatch/组合/切换组合.py Codex
```

脚本先在个人配置里找组合文件，逐行执行，任何一行失败就停，成功后写 `当前组合.txt` 并打印 `magpie groups`。切完派一个 explorer 小活，用 `magpie usage --csv --last 1h` 核对落点。

示例的 Codex 组合用 `stays=turn`，国产组合用 `stays=auto`。`stays` 管一段对话粘不粘在上次答话的模型上。turn 的理由是：主模型一次不可用会让 auto 把对话粘在兜底模型上，后续请求可能大量落到兜底；turn 让每轮新对话都先试主模型。

订阅类来源（比如 Codex）有每分钟请求上限，按账号算、所有组共用。名额满时，组里有非订阅兜底的会被 magpie 直接让给兜底，所以兜底占比突然变高，先查是不是并发开多了。

额度或质量要求变化时调组合文件本身，不新建 agent：额度紧就把强模型换成常规模型，或把 `:xhigh` 改 `:high`；额度松就反过来。改完重跑一次切换脚本。这类调整也是复盘时 `dispatch-retro` 会给你建议的地方。

## WSL 怎么用

这一节解决"Windows 和 WSL 两边怎么共用一套配置、怎么把 worker 派进 WSL"。没有 WSL 或远程执行机就跳过，worker 直接在本机跑。

WSL 里按需安装 claude、codex、uv、node。配置和 Windows 共用一份：`~/.claude/CLAUDE.md`、`agents`、`skills`、个人配置目录、`~/.codex/AGENTS.md`、`auth.json` 是指向 Windows 的链接，改 Windows 那份两边生效。`settings.json`、Codex 的 `config.toml`、MCP 是从 Windows 版生成的，Windows 那边改了这三样，要在 WSL 里重跑一次同步脚本：

```text
python3 /mnt/c/Users/<用户名>/.claude/skills/dispatch/WSL/同步配置到WSL.py
```

用法一是在 Windows 主会话里派 worker 到 WSL。Orca 通过 SSH 远程服务器连进 WSL（sshd 只监听 127.0.0.1、只认密钥）；项目先在 WSL 里 clone 一份放在 ext4 上，再登记成这台服务器上的项目。派 worker 有三种写法：新票用 `--worktree new-top-level --repo id:<repoId>` 新建工作区；同一张票返工用原工作区的精确选择器加 `--terminal <原终端句柄>`；只读审查指向要审的那个工作区。不要把 `--worktree` 直接指向主检出，那样 worker 会在主检出里改。完整命令看手册 `参考/远程执行机.md`。

用法二是在 WSL 里直接开主会话。`cd ~/work/<项目>` 后运行 `claude` 或 `codex`，规则、agent、手册都是同一份。要让会话在 Windows 的 Orca 里看得到、管得到，在 Orca 里打开这台服务器上的项目，从 Orca 的终端里起 `claude`。

不重启 WSL、不改 `.wslconfig`，除非先问过你：可能有别的项目在 WSL 里部署。

## 反馈和复盘

这一节讲这套配置怎么跟着你的用法慢慢变好。

GitHub 上的是框架，每个人的个人配置不一样：机器、额度、模型来源、对质量和成本的取舍都不同。框架靠两个技能让个人配置迭代：

- 一个批次做完，或者派活中碰到框架的问题，在项目会话里说“写反馈”。`dispatch-feedback` 按问题、代价、证据、建议、归属五栏写一份，放进个人配置的 `反馈/`。
- 隔一段时间，在任意会话里输入 `/dispatch-retro`（它不会自动触发）。它读上次以来的反馈、magpie 用量和 Orca 派活历史，必要时按关键词抽会话记录核实，然后给一份推荐清单：每条写证据、收益、代价、能不能撤回，你点头的才改，改前备份，改完记进 `复盘记录.md`。

属于框架本身的问题（规则缺失、脚本 bug、模板不好用），复盘会起草成 issue 给你看，脱敏后由你决定发不发到框架仓库。
