# 使用指南

这份文档讲怎么把这套装起来、装完怎么用、遇到常见情况该怎么办。看完你应该能判断"我这句大白话会派给谁"，以及出了事去哪找原因。

## 这套东西装完是什么样

这一节说明装完你手上多了什么，以及哪些事它管不到。

装完之后，你的 Claude Code 多了 7 个可以直接点名的子代理、一本叫 dispatch 的派活手册、一段写在全局 CLAUDE.md 里的规则。主会话还是 Opus 5.5，但它不再自己读十几个文件、自己搜网页，而是把这些活派出去，自己只留拆解、决策、验收和跟你说话。

每个子代理的 model 写的是一个角色路由组，比如 `group/explore`、`group/review`。组里具体放谁，由当前用的"组合"决定。仓库给的两份示例里，一份放 GLM、MiniMax、DeepSeek，另一份放 Codex 的 Terra、Sol、Astra 并用国产模型兜底；成员可以按自己的需要替换。换组合就是换一整套干活的模型，agent 文件不用动。

它管不到的地方也说清楚：这是配置文件，不改 Claude Code 本身的行为；模型的落点最终由 magpie 的角色组和组合决定；magpie 没开、组没建对或者组合文件里的来源没替换，子代理就可能起不来，或者落到不是你想要的地方。

## 安装

这一节解决"从下载到第一次生效"。

装之前先备份：把 `~/.claude/agents` 整个目录和 `~/.claude/CLAUDE.md` 复制一份到别处。以后想退回旧配置，直接盖回来就行。

然后按顺序做四件事。

第一，把仓库 `claude-code/agents/` 下的 7 个文件拷到 `~/.claude/agents/`。这些文件的名字就是 agent 的名字，别改名。

第二，把 `claude-code/skills/dispatch/` 整个目录拷到 `~/.claude/skills/`，目录名保持 dispatch，因为 CLAUDE.md 片段里是按这个名字引用它的。这个目录里还有 `组合/`（两份组合清单和切换脚本）和 `WSL/`（同步脚本），一起拷过去。

第三，打开 `claude-code/CLAUDE.md片段.md`，把里面那个 markdown 代码块的内容贴进 `~/.claude/CLAUDE.md`。贴在文件末尾就行，它是按小标题组织的，不依赖上下文。

第四，照 `../magpie/路由组与档位.md` 建四个档位组、把 Claude Code 的各个档位指向对应的组。然后把 `组合/国产.txt` 和 `组合/Codex.txt` 里的 `<国产来源>`、`<Codex来源>`、`<Claude来源>` 换成你 magpie 里的供应商 id，跑一次切换脚本选定一个组合。这一步最容易漏，漏了的话子代理会找不到模型。建组前先 `magpie save` 存一份快照，改坏了能 `magpie use` 回来。注意每条 `magpie claude` 命令都必须带模型值，不带值的写法会把 magpie 从该档位上摘掉。

做完新开一个会话。当前会话不会热加载 CLAUDE.md，这是 Claude Code 本身的行为，不是配置写错了。

想只在某个项目里用，就把 agent 文件放到项目根的 `.claude/agents/`。项目级和全局同名时项目级优先，可以拿它给某个仓库单独换模型。CLAUDE.md 那段规则仍然写在用户目录那份里，跟着对所有项目生效。

## 三种调用方式

这一节解决"我到底该敲斜杠还是说人话"。

第一种是 mattpocock 那套流程技能，比如 `/grill-with-docs`、`/to-spec`、`/to-tickets`、`/implement`、`/implement-spec`、`/wayfinder` 等二十来个。它们文件头写了 `disable-model-invocation: true`，只能你自己敲斜杠触发，模型不会自己叫出来。这是有意的：这些技能步骤重、会改文件，不适合被自动触发。

第二种是工具技能，比如 grilling、code-review、tdd、diagnosing-bugs、research、domain-modeling、codebase-design、prototype、resolving-merge-conflicts。说大白话有可能自动触发，但不确定，想确保跑到就敲斜杠。

第三种是 7 个具名 agent。它们默认是隐性的，你说大白话，Opus 自己判断派不派、派给谁；想指定这一次一定给它，就直接点名，或者用 `@"explorer (agent)"` 这种写法强制这一次派给 explorer。

这三种的区别值得记一下：技能是"一套流程"，agent 是"一个干活的角色"。技能里面如果要派子代理，比如 code-review 会派两个审查子代理，按派活手册第 9 节的映射换成 reviewer，不会落到 Opus 上。

## 常见说法对应什么行为

这一节用几个真实会说的话，帮你建立"我这么说，会发生什么"的直觉。

你说"这个项目我两周没碰了，看看做到哪了"，Opus 会派 explorer。它会先读项目根的 CLAUDE.md、AGENTS.md、README，再看 `git log --oneline -20` 和 `git status`，回来给你一份带文件路径和行号的结论清单，不超过 40 行。

你说"让 researcher 查一下 X 最新版有没有支持 Y，只要官方来源"，它会去查官方文档、仓库源码和官方接口，每条事实标已核实或未核实并附链接。版本号这类会变的数据它会走官方接口而不是网页，因为网页可能读到缓存。

你说"我刚改了 cleanup.py，看看有没有问题"，Opus 派 reviewer。审查结果每条带 `文件:行号`、触发条件和严重度，站不住的结论它自己会删掉。

你说"日志里一直报 503，查查原因"，派 diagnoser。它第一句会先问你哪台机器、哪个环境、哪个服务，没问清就停下来，不会跑到本机上去猜别的机器的问题。它只跑只读命令，交付是现象、证据、按可能性排序的原因、每个原因的验证命令、建议修法和回滚方案。

你说"把这几张截图里的数据整理成表"，派 extractor。它只处理你给的材料，材料里没有的字段写"原文未提及"，不补全也不润色。它不上网，所以别让它判断"外面有没有这条信息"。

你说"把这些定下来的结论写成一份交接文档"，派 writer。它只写你指定的路径，写完交回来验收，不往外发。

一个开发流程走下来是这样的：`/grill-with-docs` 拷问需求，`/to-spec` 出规格，`/to-tickets` 拆票；然后离开 Opus 会话，用 `claude --model group/glm-main` 开一个实现会话，每张票跑 `/implement`，两张票之间 `/clear` 防止上下文越滚越长；回到 Opus 会话跑 `/code-review`，它并行派两个 reviewer，一个查编码规范、一个查需求符合度；合并和 push 之前会问你。

要并行时，你说"这两张票互不依赖，开两个 Orca worker 并行做"。Opus 会给每张票写一份自包含的任务说明，用独立 worktree 起 worker。并发上限可按下节的建议设置。worker 干完停在"改完未提交"，不会自己 commit。

## 实现类任务怎么派

这一节解决"要改代码的活交给谁、任务说明写到什么程度"。

子代理是只读设计的，改代码走两条路：Orca worker，或者你自己开一个实现会话。

Orca worker 分几种：常规实现用 `group/impl`，复杂、跨模块、需要判断的用 `group/impl-strong`，还有一个守望者用 `group/minimax`，专门盯外部 agent 的会话，只发"继续"，遇到非上游原因的阻塞只报告不介入。想用 Codex 自己的工具链，可以起 Codex 原生 worker，命令里写 `--agent codex --model gpt-6.1-sol`，难活用 `gpt-6-astra`，机械活用 `gpt-6.1-terra`。Codex 原生 worker 不读 `~/.claude` 下的规则，派活说明里的固定规则要原样抄进去。启动命令和参数看派活手册第 4 节，先跑一次 `orca skills get orchestration` 读和当前版本匹配的指南。

推理档位每次派 worker 时由 Opus 按难度定，只用三档：

- medium：机械活，按明确清单改文案、重命名、批量替换、跑一遍给定命令收集输出。
- high：常规实现，范围清楚的功能、补测试、修有复现步骤的 bug。拿不准时用它。
- xhigh：难活，跨模块改动、并发/安全/数据迁移、没有复现步骤的 bug、上一次返工过的任务。

示例使用这三档，可按模型能力、任务质量和费用调整。示例组的配置是：Codex 成员写成 `:medium+high+xhigh`，GLM 和 DeepSeek 钉 `:high`，MiniMax 写成 `:medium+high+xhigh`。传了范围外的档位，magpie 会换成最接近的那一档。

建议按上游限流、额度和本机资源设并发上限，避免请求拥堵和构建争抢资源。例如总共 7 个、其中 Codex 最多 4 个，超出 Codex 上限的任务可交给有余量的兜底模型；同时运行的原生子代理也应计入对应上游的并发。WSL 构建和测试的数量按机器资源确定。长时间连续运行也可按自己的情况设置时长和检查间隔。

任务说明要自包含，worker 不需要回来问你就能干。里面写清楚：一句话目标；基线，包括基准提交、规格文件路径、必读文件（项目的 CLAUDE.md 和 AGENTS.md 必列）；允许改哪些文件、禁止碰什么；你已经跑过的现状，比如"当前 3 个测试红"；完成判据，也就是要跑哪些测试、预期什么结果；失败怎么算，非零退出算失败，还是收集失败信息本身就是交付物。

实现者还有几条固定附加规则：先读规格和 AGENTS.md，不回退别人的改动；Bash 每次只跑一条直接命令，不加 `cd`、不用 `&&` 和管道；测试先定向后全量，真实捕获退出码，不凭输出末尾判断通过；停在改完未提交。

不开 Orca 也行。直接开一个主模型指向 `group/glm-main` 的会话，跑 `/implement`、`/tdd` 这类流程技能，每张票之间 `/clear`。

## 子代理和独立会话的区别

这一节解决"什么时候该派子代理、什么时候该另开会话"。

子代理是在当前会话里分出去的，有自己的上下文，干完把结果交回来就结束，你没法再给它追加指令。适合一次能说清、不需要来回追问的活。

独立会话是一个完整的 Claude Code 进程，有自己的主模型，你可以持续跟它对话、追加指令。Orca worker、手动开的实现会话、`claude -p` 都属于这一类。

有个容易搞混的点：Claude Code 的独立会话一样能用 `~/.claude/agents` 里的 agent，而 agent 用哪个模型只看它自己文件里写的，和谁派它无关。所以哪怕是在一个主模型是 GLM 的会话里，你点 reviewer，它还是跑在 `group/review` 上。至于 `group/review` 里是国产模型还是 Codex，看当前组合。

Codex 有两种接法，别混。用 `--agent claude --model group/impl` 时，起的是 Claude Code，只是模型由 magpie 路由到 Codex，这套 agent 文件和规则照常生效。用 `--agent codex` 时，起的是 Codex 自己的进程，它不读 `~/.claude` 下的任何规则，这套配置对它不生效。

## 新项目怎么开始

这一节给从零开始的项目一条最短路径。

先 `git init`。Orca 的独立 worktree 和 code-review 都依赖 git，没有 git 这两样都用不了。

然后跑 `/setup-matt-pocock-skills` 初始化技能产物。一个人用的话，推荐选本地 markdown 放在 `.scratch/` 里，省去配外部服务的麻烦。

之后走主流程：拷问、出规格、拆票、实现、审查。跑起来之后，项目根会慢慢长出自己的 CLAUDE.md 和规格文档，后面每次派活的质量都会跟着变好。

## 老项目怎么接手

这一节给已经有一堆代码、可能还没文档的仓库一个入口。

先派 explorer 摸底，让它读结构、找入口、看 git 历史，把现状写成带行号的清单。这一步很关键，后面所有判断都建立在它上面。

如果仓库里没有 CLAUDE.md 或 AGENTS.md，让 writer 根据 explorer 的结论起草一份，你看过再定稿。没有这份东西，子代理每次都得从零摸索。

是 git 仓库就把 mattpocock 技能初始化一下。要重构就用 `/improve-codebase-architecture`，出了 bug 就用 `/diagnosing-bugs`，它会派 diagnoser 只读取证。

如果目标目录不是 git 仓库，那就只能用原生子代理，Orca worktree 和 code-review 都用不了，这个限制绕不过去。

## 报错和改派

这一节解决"跑挂了怎么办"，重点是别盲目重试。

GLM 内容审核的 1301 是最常见的。GLM 偶尔会把正常内容判成敏感，报错藏在 HTTP 200 的响应流里，网关的故障转移接不住，所以看起来像成功其实没产出。处理办法有两个：同一个 agent 用 `model="haiku"`（指向 MiniMax）重派一次，或者在回复里说一句"我换了个模型重派"；如果是长任务、对准确性要求高，改成 Orca worker 指定 `group/ds-flash`。遇到错误时先核实原因，再选择可用的替代模型。

503 No available accounts 和 429 是号池满或限流，等一会儿重派；连续失败就把模型降一档，例如把主力模型换成同来源更快的模型。

其他报错先看原文再决定，不要照着上一条的经验乱试。同一种方法连续失败两次，停下来查文档。

还有一条经验：MiniMax 只派结果能校验的活，比如有原文可对照、有路径可核的。它不知道的时候倾向于编，所以别让它判断"外面有没有这条信息"。实现类也不要派给它。

## 验收和 git 规则

这一节讲怎么判断一次派活算不算完成，以及什么时候能动 git。

worker 交付必须带凭证：改动范围（`git diff --stat`）、测试命令和通过数、实际用的模型、没解决的风险。主脑按凭证核对，只对缺口和矛盾的地方复查，不重跑全部。部分通过不算完成。不通过就把修正意见发回原 worker，主脑不自己上手改。

git 上的规矩是：mattpocock 那套流程可以在功能分支上本地 commit，因为 code-review 要拿提交点来比对改动范围；但不直接提交 main 或 master；push 和合并等你同意。Orca worker 始终停在改完未提交。

## 核对模型落点

这一节教你怎么确认钱花在了该花的地方。

跑 `magpie usage --csv --last 1h`，看 `requested_model`、`served_model`、`effort` 三列。requested 是你要求的角色组或档位组，served 是实际落到的模型，effort 是推理档位。三个都对上，说明配置生效了。

如果发现有活落到了 Opus 上，最常见的原因是用了内置 Explore、Plan 这类子代理。官方文档说，内置 Explore 的模型由 Claude Code 按环境决定：经 `ANTHROPIC_BASE_URL` 网关（比如 magpie）时跑在 `opus` 别名指向的模型上，部分云平台上则跟随主会话。总之它可能落到 Opus，而且不受你的 agent 文件控制，所以摸底用自带的 explorer 更便宜也更可控。另一个原因是 `general-purpose` 传了 `"opus"`，在主会话是 Opus 时那等于派给 Opus 自己。

如果 `requested_model` 是角色组，但 `served_model` 不是你期望的模型，先 `magpie groups` 看这个组里现在是谁，再看当前组合是不是你切的那个。

## 升级模型和换供应商

这一节解决"模型换代了要改哪里"。

角色组改组合文件：把 `组合/国产.txt` 或 `组合/Codex.txt` 里的模型名换掉，再跑一次切换脚本。比如 GLM 出了新版，就把 `glm-5.3` 改成 `glm-5.5`，然后切一次国产组合。agent 文件、派活手册、Orca 命令全都不用动。

档位组直接改成员：`magpie group set glm-main models=<来源>/<新模型名>`。

`<来源>` 是你 magpie 里的供应商 id，用 `magpie providers` 能看到。组名和成员名都别写版本号，版本号只出现在组成员的具体模型名里。

## 组合怎么切

这一节解决"什么时候切、切完怎么确认"。

组合就是"每个角色组里放谁"的一份清单，放在 `~/.claude/skills/dispatch/组合/`。仓库里的国产示例用 GLM / MiniMax / DeepSeek，Codex 示例用 Terra、Sol、Astra 并排国产模型兜底；两份都只是参考写法。

角色组和档位组是两回事。角色组按"干什么"命名，agent 和 worker 用，示例里一共九个；组合换的就是这九个组里的成员。档位组按 Claude Code 的 opus、sonnet、haiku、fable 别名命名，给没有写死角色组的地方用，比如 `general-purpose` 和手动开的实现会话；切组合不动档位组，只有换供应商或升级模型时才单独改。

两份组合是参考示例，不是推荐方案。按自己的供应商、额度和任务质量要求调整：探索和抽取可选快、成本较低的模型，审查和复核可选能力更强的模型；照现有文件新增清单即可创建自己的组合。两边使用同一批 agent 和规则，切换改变的是角色组成员。

切换命令：

```text
# Windows
python "$HOME\.claude\skills\dispatch\组合\切换组合.py" Codex
# WSL
python3 ~/.claude/skills/dispatch/组合/切换组合.py Codex
```

脚本逐行执行组合文件里的 `magpie group add`，任何一行失败就停，成功后写 `当前组合.txt` 并打印 `magpie groups`。切完派一个 explorer 小活，用 `magpie usage --csv --last 1h` 核对落点。

示例的 Codex 组合用 `stays=turn`，示例的国产组合用 `stays=auto`。`stays` 管一段对话粘不粘在上次答话的模型上。turn 的理由是：路由先主后备时，主模型一次不可用会让 auto 把对话粘在兜底模型上，后续请求可能大量落到兜底；turn 让每轮新对话都先试主模型，试不上才顺延。其他组合按自己的路由需要选择 auto 或 turn。切换前已经开始的对话可能还留在旧模型上，核对时看切换后新开的对话。

额度或质量要求变化时调组合文件本身，不新建 agent。示例里额度紧可以把 Astra 换 Sol、Sol 换 Terra，或把 `:xhigh` 改 `:high`；额度松就反过来。改完重跑一次切换脚本。

## WSL 怎么用

这一节解决"Windows 和 WSL 两边怎么共用一套配置、怎么把 worker 派进 WSL"。

WSL 里按需安装 claude、codex、uv、node。配置和 Windows 共用一份：`~/.claude/CLAUDE.md`、`agents`、`skills`、`~/.codex/AGENTS.md`、`auth.json` 是指向 Windows 的链接，改 Windows 那份两边生效。`settings.json`、Codex 的 `config.toml`、MCP 是从 Windows 版生成的，Windows 那边改了这三样，要在 WSL 里重跑一次同步脚本：

```text
python3 /mnt/c/Users/<用户名>/.claude/skills/dispatch/WSL/同步配置到WSL.py
```

不传参数时脚本会用 `cmd.exe` 读 `%USERPROFILE%` 再转成 `/mnt/c/...`；推断不出来就要求你把 Windows 家目录作为第一个参数传进去。magpie 只有 Windows 一份，WSL 是 mirrored 网络，直接用；代理也是走本机回环地址。有几个 MCP 依赖 Windows 专用路径，在 WSL 里带不过去，脚本会跳过并列出名字，要用就在 Windows 会话里做。

用法一是在 Windows 主会话里派 worker 到 WSL。当时的 Orca 版本里，"把 WSL 发行版直接当主机"这个功能在内部开关后面，界面上找不到，所以走 Orca 的 SSH 远程服务器：sshd 只监听 127.0.0.1、只认密钥登录。项目要先在 WSL 里 clone 一份放在 ext4 上，再登记成这台服务器上的项目：

```text
orca project setup-existing-folder --host runtime:<envId> --path /home/<用户>/work/<项目>
```

登记后拿到 repoId，派 worker 时比 Windows 多 `--on <服务器名>`，`--worktree` 写 `id:<repoId>::<WSL路径>`：

```text
orca orchestration worker-start --on <服务器名> --worktree "id:<repoId>::/home/<用户>/work/<项目>" --spec-file <说明.md> --task-title "<标题>" --agent claude --model group/impl --effort <档位> --keep-open
```

远程主机上 Orca 起的是终端模式 worker，不是结构化会话，一样能在 Orca 界面里切过去看、插话，`check`、`send`、`worker-release` 用法不变。依赖在 WSL 里单独装，不链接 Windows 检出里的。同时在 WSL 里跑构建或测试的 worker 数应按机器资源确定。

如果 worker 启动报 `agent_prompt_blocked`，多半是 claude 首次运行的提示卡住了。先 `orca terminal read` 看是什么提示，回答后把对应的"已看过"键加进同步脚本。已知一个是"要不要把 auto 设为默认权限模式"，对应 `~/.claude.json` 里的 `hasSeenAutoDefaultNudge`，脚本已经处理。

用法二是在 WSL 里直接开主会话。`cd ~/work/<项目>` 后运行 `claude` 或 `codex`，规则、agent、派活手册都是同一份，原生子代理照常派。要让会话在 Windows 的 Orca 里看得到、管得到，不要在裸 WSL 终端里起，而是在 Orca 里打开这台服务器上的项目，从 Orca 的终端里起 `claude`。切组合用上一节的 WSL 命令。

不重启 WSL、不改 `.wslconfig`，除非先问过你：有别的项目在 WSL 里部署。
