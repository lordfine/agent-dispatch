# 派活手册

## 0. 先读个人配置

个人配置在 `~/.claude/派活配置/`（环境变量 `DISPATCH_CONFIG_DIR` 可改；旧路径 `~/.claude/skills/dispatch/本机/` 是指向它的联接，照样能用）。派活前先读里面的 `本机条件.md`：在用组合、并发、额度、机器、有没有远程执行机、模型禁忌。没有这个目录或文件时，先用 `dispatch-retro` 走初始化引导，不凭空假设。

资源分机器（CPU、内存、有没有 WSL/Docker、能开几个测试进程和浏览器）和额度（模型来源、订阅还是按量、每分钟请求上限、预算）；具体数值只写在个人配置里。资源紧时依次减并发、降推理档、换常规模型（impl-lite 或 impl），最后才减审查；验收标准不随资源降低。资源充裕时反过来，可以多开并发、用强模型、多人核验。

框架分三层，按个人配置里有的用：基础层只有 Claude Code 或 Codex，用原生子代理；底座层加 Orca（worker）和 magpie（角色路由组）；进阶层加 WSL 或远程执行机、多模型组合。下面第 7 节的参考篇开头写了各自需要哪一层，只读和当前任务相关的那篇。

主脑负责拆解、决策、验收和用户沟通；少量文件的小改动、看几张截图可以自己做。框架会话向项目会话转达规则时，标明用户原话或建议；如与用户意思冲突，以用户为准，接收方先问用户。项目记忆不记派活口径，只留一行指向本手册。

## 1. 派给谁

每个角色对应一个 magpie 角色路由组，组里现在是谁由个人配置里的在用组合决定（见 `参考/组合与路由.md`）。看当前组合和各组成员时，读个人配置的 `组合/当前组合.txt`、对应组合文件和 `magpie groups`；成员和兜底顺序以组合文件为准。

原生子代理（只读或短活，结果直接回到主会话）：

| agent | 干什么 | 路由组 |
|---|---|---|
| `explorer` 探索员 | 摸代码、找定义和调用链、恢复项目现状 | `group/explore` |
| `researcher` 尽调员 | 网上调研、选型对比、核实说法 | `group/research` |
| `extractor` 转录抽取员 | 日志/周报/表格/批量截图的逐字转录和抽取 | `group/extract` |
| `reviewer` 审查员 | 代码或方案审查；安全轴、正确性轴可分两次派 | `group/review` |
| `diagnoser` 诊断员 | 线上/本机/服务器排障取证，只读，给假设+验证命令+回滚 | `group/diagnose` |
| `writer` 文档员 | 把定好的内容写成交接文档、进度文档、员工物料、JD 初稿 | `group/write` |
| `verifier` 复核员 | 关键决策复核、高风险最终验收、冲突裁决（少用） | `group/verify` |

Orca worker（要改代码、耗时长、要并行、要别的 agent；怎么起见 `参考/Orca.md`）：

| 角色 | 怎么起 | 用途 |
|---|---|---|
| 轻量实现者 | `--agent claude --model group/impl-lite` | 清单式的确定性活：固定清单的断言对齐、文案、字段替换、已定位的小修 |
| 实现者 | `--agent claude --model group/impl` | 需求明确、范围清楚的实现；配 `--effort xhigh` 也能接难活 |
| 高级实现者 | `--agent claude --model group/impl-strong` | 复杂、跨模块、需要判断的实现；组里放不放比 impl 更强的模型由个人组合决定，第一顺位和 impl 相同时就等于 impl 加高档 |
| Codex 原生实现者 | `--agent codex --model <裸模型名>` | 只在需要 Codex 自己的工具链或做对比时用 |
| （手动） | `--model <用户指定的组名>` | 仅用户点名时 |
| 守望者 | `--model haiku`（haiku 档位指向见组合文件） | 盯外部 agent 会话，只发“继续”，非上游原因的阻塞只报告不介入 |

这三个实现组只是分组定义，组里放谁、放不放强模型，用户按自己的额度和喜好在组合文件里定。三个组都不写死推理档位，由主脑每次用 `--effort` 决定（第 4 节）。

## 2. 硬规则

- 调用具名 agent **不传 `model`**，让 frontmatter 生效。
- **不用内置 Explore / Plan**：它们的模型由 Claude Code 按环境决定，可能落到 Opus，也不受 agent 文件控制；具名 explorer 更便宜、更可控。
- `general-purpose` 不得已要用时传 `model="sonnet"` 或 `model="fable"`；具体落点以在用组合为准。别名档位从大到小是 fable、opus、sonnet、haiku，各自用途见组合文件注释。Opus 主会话里不要传 `model="opus"`：同家族时 Claude Code 直接用主会话的 Opus，不走档位（11-03 实测）。不写 model 的子代理落到 subagent 档位。
- 便宜模型不知道时容易编：只给它派结果能校验的活（有原文可对照、有路径可核），不派“判断外面有没有这条信息”的活。哪些模型属于这类见个人配置。

## 3. 报错改派

- 智谱内容审核 1301：按个人配置里的改派规则执行。
- 503 No available accounts / 429 / 连接断开：组内兜底由 magpie 按顺序自动顺延，主脑先等一会儿重派；连续失败就把 impl-strong 的活改派 impl，或把 xhigh 降到 high。还不行就跑 `magpie accounts <来源>` 看额度，问用户要不要切组合，不自己切。
- 其他报错先看报错原文再决定，不盲目重试。

## 4. 定档：风险档和推理档

派活前先定风险档，写进规格开头（`模板/规格.md`），回复里说明定了哪一档、为什么；拿不准按中档：
- 小档：文案、重命名、配置、批量替换。规格只写目标、范围、完成判据三行；只跑相关测试，主脑看凭证验收，不派 reviewer。
- 中档：范围清楚的功能或有复现步骤的 bug。规格四栏各一两句；先写一条会失败的测试再实现，交付附改前失败和改后通过的证据。主脑看改动统计和凭证，齐全即通过；集成时一批中档票合起来只派一个 reviewer，对照各票规格审合并后的改动。单票超过约 300 行或 10 个文件、涉及权限/鉴权/数据写入/对外接口、或 worker 交付写了“拿不准”，这三种情况当场派 reviewer。
- 大档：跨模块、安全、数据迁移、没有复现步骤的 bug、返工过的活。规格写四栏；规范轴和需求轴各派一个 reviewer，关键任务再派 verifier 给逐项证据表。安全类大档票的安全轴审查不能省，“只许收紧、不许放宽”写成审查员的检查项（实战项目批14：返工时权限被悄悄放宽，测试全绿，只有安全轴逐条核才发现）。

推理档位每次派 worker 由主脑判断，必须带 `--effort`，并和 `--model` 一起用。只用 `medium`、`high`、`xhigh` 三档，不用 low、max、ultra（2026-11-06 作者定：没有哪件事需要 max，那是多余的开销）。
- `medium`：固定清单的断言对齐、文案、字段替换。
- `high`：已定位、边界明确的修复与补测，拿不准时默认它；权限、迁移、跨模块任务先按状态复杂度判断，拆出确定性子任务后才试 high。
- `xhigh`：方案性工作、并发、异步恢复、外部结果未知和不可逆迁移；前端开放设计和视觉用 impl-strong + xhigh。

确定性的活可降一档推理或改用 impl-lite，允许首次交付后按明确反馈补一轮（two-shot）；前端设计、非标准任务用强模型和高档。验收标准不随档位下降。`xhigh` 必须写明属于上面哪类难活，写不出就降到 `high`；集成、检查、复现默认 `high`。派活回复写明档位和理由。原生子代理不传 `effort`（实测传了也会被冲成 high），它的档位钉在组合文件的组成员上（细节见 `参考/组合与路由.md`）。

并发上限、连跑和额度检查见个人配置。并行改代码时，每个 worker 使用独立工作区（仅 git 仓库）。订阅类来源（如 Codex）的每分钟请求上限按账号算、所有组共用，开多了主要在排队，见 `参考/组合与路由.md`。

## 5. 任务说明（spec）怎么写

照 `模板/规格.md` 写：开头写风险档、确定性、推理档，返工时补返工原因（派活记录要用）；正文写清目标、基线、允许改和禁止碰的范围（别人的改动、配置、线上）、已知现状、完成判据和失败口径；基线包含提交、规格路径和项目 CLAUDE.md / AGENTS.md 等必读文件。模板末尾的“实现者固定规则”原样带上。主脑能查的事实自己查，只把需要决定的事交给用户。只传路径、提交、票号等指针，不粘贴全文；每张票完成后换新会话，只带下一张票和凭证。

中档、大档写四栏：外部行为、改动接缝、测试决策、不做什么。外部行为要写必须保留的现有能力（旧入口、状态、权限、数据完整性）；不做什么默认包含不新增持久状态或机制，要加表、标志、租约或认领，先说明必要性，由主脑拍板。

“缺了 X 就拒绝”这类收紧改动，规格里要求 worker 用 grep 找出所有直接调用被收紧入口的测试（不只按主题挑文件），逐处说明为什么不受影响；主脑不把定向全绿当成集成全绿，集成后跑全量再上线（实战项目批14：定向 13 个文件全绿，全量炸 18 项）。

改全局语义（隐私、编号、仓库模型这类共享契约）的票单独先发，合入后马上跑全量，不等凑批；一批 5～6 张票。任务拆成可独立验收、一个 worker 会话装得下的竖切片，依赖用 `task-create --deps` 表达。已验收且没有依赖的分支单独集成；主会话列出可上线清单，一次性向用户确认上线授权。

## 6. 验收

实现者交付必须带凭证：改动范围（`git diff --stat`）、测试命令与通过数、实际使用的模型、未解决的风险。交付格式见 `模板/交付.md`；要在 WSL 跑测试的审查用 `模板/WSL审查.md`。
- 主脑按凭证核对，只对缺口或矛盾复查，不重跑全部。
- **部分通过不算完成**。不通过就把修正意见发回原 worker（`参考/Orca.md`），不自己动手改。
- 返工两轮后还冒出相邻的新问题，就停下来对比基线，判断新增的状态或机制是否必要，再决定撤回、拆票还是继续，不再叠补丁。
- 冻结线（11-09 作者定）：只有高严重、相对基线的回归、真安全控制问题阻断发版；基线已有的中低问题和纯边界情况进下批待办。按实际影响判断：基线问题被本批扩大、影响数据完整性或撤权的，照样阻断。
- 审查核验（试行）：审查查出的问题，默认由一名独立核验者复现原反例；真安全控制、恢复、迁移、高影响或核验有分歧时再加人，保留盲态抽样和“原问题是否已关闭”的核销。用工作流做审查时同样按这条，不默认每条发现三票。
- 全量测试：集成前和发版前各跑一次；大档票和改全局语义的票，交付前再跑一次，不等待地排队，被占就跳过并在交付里写明。一台测试机同一时间只跑一个全量，用排队脚本挡，不靠各会话自觉。怎么跑、怎么提速见 `参考/验收与测试.md`。审查员只跑复现问题所需的最小用例。
- Orca worker 的 commit，以及所有 push、合并进主分支、发版、对外发送，由主脑在用户同意后做（mattpocock 流程的本地 commit 例外见 `参考/配合其他技能.md`）。
- 派活记录：规格开头那几项就是记录的人工部分，其余（派出、完成时间、返工链、模型、测试数）由脚本从 Orca、magpie 和交付文件拼，格式见 `模板/派活记录.md`。
- 每个项目每完成一个批次，项目会话用 `dispatch-feedback` 写反馈进个人配置的 `反馈/`；之后用 `dispatch-retro` 复盘，机械性问题做成检查，需要判断的问题写成规矩。
