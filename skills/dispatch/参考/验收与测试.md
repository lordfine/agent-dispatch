# 验收与测试

需要：基础层。全量排队脚本需要 Linux 的 `flock`（WSL 或 Linux 执行机都有）。

## 全量测试什么时候跑

全量由主脑在 worker 会话外跑，worker 只跑定向测试（2026-11-16 作者定）。原因：worker 会话里跑全量占着 worker 的上下文和测试机资源，几个 worker 同时跑会把开发机拖到卡顿，而且结果常常不全绿、worker 也判断不了是不是本票造成的（实战项目批19、批22 各一次）。

- 集成前、发版前各跑一次，必须拿到结果，用等待方式排队。
- 大档票和改全局语义的票交付后、合入前，主脑用不等待的方式排一次：拿到名额就跑，被占就记进主脑的待补清单，空出来再补，不让 worker 等。理由是晚发现的代价远大于一次全量（实战项目批15：隐私票合入后埋下的 142 项失败 17 小时后才暴露，接着返工 3 轮）。
- worker 只跑定向测试；返工后只重跑失败和受影响的测试。审查员只跑复现问题所需的最小用例。
- 全量的运行号和结果写进验收记录；交付模板里的“全量”一栏由 worker 写“交主会话排队”。

## 多个会话之间不冲突

一台测试机同一时间只跑一个全量，用 `脚本/全量排队.sh` 挡，不靠各会话自觉：
```text
bash <本技能目录>/脚本/全量排队.sh --status
bash <本技能目录>/脚本/全量排队.sh --no-wait --label "<票名>" -- bash <项目的全量脚本>
bash <本技能目录>/脚本/全量排队.sh --wait-minutes 180 --label "集成前" -- bash <项目的全量脚本>
```
`--no-wait` 被占时退出码 75，用于大档票交付前；集成前、发版前用等待方式。`--status` 显示谁占着、从几点开始。

起跑前预检（排队前跑，没过退出 3，不占名额）：
- 当前目录有未提交的合并就拒跑。全量只在“合并提交之后、推送之前”判；没过就 `reset` 回合并前再说，不在未提交的合流状态下判全量（实战项目批14：依赖当前提交的测试在未提交合并里必挂）。确实要在合并中途跑，加 `--allow-merge-in-progress`。
- 项目预检：项目在 `.dispatch/全量预检.sh`（或 `.py`）里写自己的起跑条件，脚本自动找；也可以 `--preflight <脚本>` 指定。常见条目：测试库的迁移版本等于仓库的迁移头、构建占位文件在（如 `frontend/dist/index.html`）、依赖装齐（Node 包、Python 虚拟环境）、工作目录是仓库根。没过就非零退出并打印补救命令（实战项目批12～14、实战项目批23：测试库落后迁移头、新工作区缺构建占位、缺 Node 包、SSH 没切目录，每次白跑一轮全量）。
- 项目的全量不在 Linux 上跑（比如直接在 Windows 跑 pytest、没有 `flock`）时，主会话起全量前手动跑一遍这个预检，口径相同。

拿着名额时，脚本给命令一个每次不同的 `FULL_TEST_RUN_ID`。项目的全量脚本要做到：
- 日志、junit、临时目录用 `FULL_TEST_RUN_ID` 拼目录名，不用固定名，更不要跑前 `rm -rf` 固定目录（实战项目11-09 核查：固定日志目录两会话同跑会互删）。
- 测试库的 schema、库名、角色名用随机名，不用固定名。
- 全量在跑时，不重启测试库容器、不改数据库参数（会掐断正在跑的连接），这类动作先 `--status` 确认空闲，再拿名额做。

共享资源算账：测试库的连接上限要大于“进程数 × 每进程峰值连接”，两份全量同时跑会翻倍，这是排队的主要原因（实战项目实测：12 进程峰值 97 连接，上限 200）。

## 全量怎么跑得快

pytest 默认用 pytest-xdist 的 `-n <进程数> --dist loadfile`（进程数见个人配置）：按文件分组，同一个文件里的用例留在一个进程，抢固定锁或共享状态的用例不会被拆开；`--basetemp` 放到 `/tmp` 下。其他测试框架用各自按文件分片的办法。

提速先测量，再按瓶颈下手：
1. 先看加进程有没有用：进程数翻倍，墙钟几乎不变，说明瓶颈不在并发，而在单个用例的成本（实战项目11-09：8 进程 47 分半，12 进程 49 分半）。这时继续加进程只会撞连接上限。
2. 单个用例贵，常见原因是每个用例都重新建表、跑迁移、写种子。优先用数据库模板克隆（PostgreSQL 的 `CREATE DATABASE ... TEMPLATE`，按文件拷贝，比重建快得多），模板全局建一份、各进程共用；从模板来的库不再跑迁移。
3. 固定的 advisory 锁会让各进程的迁移排队；能按 schema 区分的键就带上 schema。
4. 拖尾：`--dist loadfile` 按文件分配，最慢的那个文件决定下限。用 junit 结果按文件算耗时，找出最慢的几个。只有抢固定锁或共享状态的文件才需要留在同一进程：给这些文件打 `xdist_group` 标记，改用 `--dist loadgroup`，其余用例逐个分配（`worksteal` 不认 `xdist_group`，pytest-xdist 3.8.0 源码核实）。改分配方式后要对比一次耗时和失败数。
5. 测试专用的数据库可以关持久化：`fsync`、`synchronous_commit`、`full_page_writes` 关掉，数据目录可放 tmpfs；只用于测试库。

集成时，测试机是 Linux（WSL 或远程执行机）而用户在 Windows 本机用的，补一步 Windows 本机导入冒烟：在 Windows 检出里把后端主模块 import 一遍、前端 build 一遍，确认没有只在 Linux 下成立的路径、编码或依赖问题。

脚本、日志和交付存档不放 `/tmp`：WSL 重启或系统清理会把它清掉，返工时就找不到上一轮的证据。放项目的本地缓存目录（如 `.本地/`）或工作区的 git 目录下。pytest 的 `--basetemp` 这类跑完即弃的临时目录不受这条限制。

跑完挂了，先把失败的文件单独串行复跑一遍，分清是并行引起的还是真有问题。墙钟类性能断言在并行下会抖，并行时不判、全量后单独串行跑一遍再判；这一遍也要在名额里跑，别被别的会话的负载污染。

单独跑能过、全量跑挂：先比对两次运行的临时目录（如 pytest basetemp）、工作目录、环境变量和目录权限，再怀疑测试之间互相污染（实战项目批13：WSL 工作区目录 775 引出 47 个假失败）。验收真数据库通过时看跳过数，不只看退出码（实战项目批13：连接串没传进去，PG 用例全部静默跳过，pytest 照样退出 0）。

## 合并和提交前的核对

- 两张并行票改了同一个共享夹具或契约文件：后合入的那张，先把主线（含先合的那张）并进它的工作区，再跑全量和前端测试，过了才合（实战项目批13）。规格里要求 worker 列出“本票会改哪些共享夹具”，主脑拆票时据此排先后。
- 主脑提交前跑 `git diff --cached --name-only`，拦下根目录的 `交付-*.md`、截图和 worker 的临时文件，不让它们进仓库（实战项目批10）。
- 接收交付用 `git status --porcelain`，连未跟踪的新文件一起看；`git diff` 不含未跟踪的新测试（实战项目 实战项目非破坏性优化批）。

## 派审查员

- 措辞用中性词：权限类审查写“读取范围核对”“写入范围核对”“数据口径核对”，不写“越权、重放、泄露、攻击”这类词。Codex 的安全过滤会直接拒绝，审查员当场停掉，而且会顺着路由组退到兜底模型（实战项目批13、批14：一次拒绝把后面一整夜的审查都带到了更贵的兜底模型）。
- 每个审查员用自己的测试库，库名写进派发提示（如 `<票>_r<轴>`，附建库和升级到迁移头的命令）；主会话的全量固定用另一个库。测试夹具会整表清理，几个人共用一个库会互相清掉（实战项目批14）。
- 审查员写的复现测试写成“修好后应通过”的形式；确实要先证明问题存在，就拆成修复前、修复后两段，文件名标明。只断言“有 bug 的前提”的测试，修好以后反而显示失败，主脑容易误判（实战项目批12）。
- 测试失败先分清“预期过时、测试构造错、产品错”，没复现之前对用户只说“测试失败，原因待查”（实战项目批13）。

## 界面验收和浏览器

- 界面验收按真实可用视口，不按整屏分辨率：2560×1440 屏幕用 viewport 2560×1300，1920×1080 屏幕用 1920×940（扣 Windows 任务栏和浏览器标签栏、地址栏）；主证据是视口截图，整页长图只作补充（2026-11-08 作者定）。手机端现在不做、不验收，规格和截图里不写手机视口（2026-11-11 用户原话“手机端视图现在不用搞，强调几次了，一直不听。”）。写界面类任务说明时把这条抄进去。
- Playwright 在 WSL 或远程执行机里无头运行，负责自动回归；ego-browser 只装在 Windows 本机，负责 agent 手动验收、截图和登录态操作。派到 WSL 的 worker 没有 ego-browser，规格里要浏览器验收就写 Playwright，或者留给 Windows 主会话做。默认使用 agent 专用配置（见 `模板/浏览器.md`，profile 见个人配置），不碰用户登录态；需要登录态的任务串行执行，不清理状态，提交、发送、删除前先问用户。
