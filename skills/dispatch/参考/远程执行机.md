# WSL 和远程执行机

需要：进阶层。个人配置里没有登记 WSL 或远程 Linux 执行机就不用读；没有的话 worker 直接在本机跑，测试和 Docker 用自己已有的环境。本机的具体值（发行版、用户、远程服务器名、地址、envId、repoId、路径）见个人配置 `本机条件.md`。

执行机可以有多台（比如本机 WSL 加一台独立的 Linux 开发机）。个人配置里每台各写一段：远程服务器名、envId、项目的 repoId 和路径、资源上限（worker 数、pytest 进程数、全量进程数）。派活时按票选一台，写在派活回复里；并发和测试资源按机器分别算。全量排队脚本的锁只管它所在的那台机器，两台各跑一个全量不冲突，但如果它们连的是同一个测试库，就按一台算。下面以 WSL 为例，独立开发机的写法相同，只是不涉及 WSL 的同步脚本和 mirrored 网络。

开发机的 WSL 是 `<发行版>`（用户 `<WSL用户>`，ext4；资源见个人配置）。里面装了 claude、codex、uv、node。magpie 跑在 Windows 上时，WSL 按自己的网络模式连它（mirrored 网络可以直接用回环地址；地址和代理见个人配置）。

## 同步配置到执行机

执行机登记在个人配置目录的 `执行机.toml`（写法见 `模板/执行机示例.toml`）：每台写 `transport`（wsl 或 ssh）、`distro`（WSL 发行版名）或 `ssh_host`（`~/.ssh/config` 里的别名）、`platform`、`workdir`、`orca_name`；ssh 的执行机另写 `magpie_url`，填执行机能连到的网关地址，不能是回环地址。项目里只引用执行机的名字。

在主机上跑：
```text
python <本技能目录>/脚本/同步执行机.py --列出
python <本技能目录>/脚本/同步执行机.py <名称>              # 只预览，列出每项是新建、替换、不变还是跳过
python <本技能目录>/脚本/同步执行机.py <名称> --执行       # 写入：先备份，写完各调一次 claude 和 codex 验证
python <本技能目录>/脚本/同步执行机.py <名称> --装CLI      # 预览要装的 CLI 版本；加 --执行 才装，只装不同步配置
```

- 已经正常工作的执行机不自动重同步。要同步先跑预览，把要替换的项和变化的键给用户看，用户同意再加 `--执行`。
- 同步的是一份固定清单：`CLAUDE.md`、agents、skills、个人配置目录、Codex 的 `AGENTS.md` 和 `agents/`、`~/.agents/skills`，另外从主机版生成 `settings.json`、Codex 的 `config.toml` 和 `~/.claude.json` 里的 MCP。WSL 上共享项建成指向 Windows 那份的链接，改 Windows 那份两边生效；SSH 上是复制过去，主机改了要再同步一次。个人配置目录里的 `备份/`（安装器和复盘留的本机备份）在 SSH 上不复制；WSL 是整目录链接，照样看得到。
- SSH 上永远不复制：认证文件、私钥、浏览器登录态、缓存、历史会话、hooks。目录里的链接会解引用后复制，解出来命中这些内容的跳过并在预览里列出；失效链接、循环链接也跳过并列出。WSL 上是整目录建链接，链接那头有什么 WSL 里就能看到什么，这层过滤管不到，所以别把敏感内容放进共享目录；生成的三份配置里不带 hooks。
- Codex 的 `config.toml` 只动几个托管键（model、model_reasoning_effort、service_tier、openai_base_url、model_reasoning_summary）：主机有的换成主机的值，主机没有的从目标删掉；model_catalog_json 一律删掉；其余（包括 model_provider 和项目信任）原样保留。
- MCP：目标 `~/.claude.json` 里的 MCP 列表整份换成从主机生成的，目标机自己独有的 MCP 会被去掉，预览里能看到。SSH 只带 HTTP/SSE 类的；请求头和 env 里的敏感项用目标机已有的值，目标没有这个值的，整个 MCP 跳过并提示。WSL 是同一台机器，规则和旧脚本一样，`.exe`、uvx、npx 这类也带过去，敏感值照搬主机的；依赖 Windows 专用路径的会跳过并列出名字，要用就在 Windows 会话里做。
- 配置里的回环网关地址（127.0.0.1、localhost 这类），在 SSH 执行机上换成 `magpie_url`；端口和 `magpie_url` 不一样的不猜：写在 env 和 Codex 配置里的会停下报错，写在 MCP 里的跳过那个 MCP。网关密钥（`ANTHROPIC_AUTH_TOKEN`、`ANTHROPIC_API_KEY`）在 SSH 上按这个顺序取：目标 `settings.json` 里已有的同名非空值，环境变量 `DISPATCH_GATEWAY_KEY`，`--密钥从标准输入`；目标已经配好时不用给。WSL 上照搬主机的值。脚本不回显、不写日志。要用户在会话里给密钥时，先说清用途、写到哪台机器的哪个文件。
- 代理类环境项（`HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY`、`NO_PROXY`，大小写都算）在 SSH 上跟随目标机：用目标 `settings.json` 里已有的同名值，没有就去掉并提示。主机为了直连本地网关常写 `NO_PROXY=*`，原样带过去会让目标机的 Claude Code 所有请求都绕开代理，只能走代理上网的机器连安装都装不上（2026-11-17 实测）。WSL 上照搬主机的值。
- 备份在目标机 `<目标家>/.dispatch-同步备份/<时间>/`。文件和目录按相对路径存原件；原来是链接的存成一个 `.链接.txt`，里面记着原指向，恢复时先把现在那项移开，再用 `ln -s <原指向> <原路径>` 重建。写到一半失败时脚本打印这些手动恢复步骤，不自动回滚；写入成功时只打印备份位置。
- 写完后的模型验证只报告结果（通过、失败、需要用户处理），验证不过不回滚，配置已经写进去了；按报告去目标机上处理。
- `--装CLI` 默认装和主机相同的版本（`--claude版本`、`--codex版本` 可指定），不用 sudo、不改 PATH 配置文件；装完 PATH 里找不到时会提示。先装 Claude Code 再装 Codex，前一个失败就停，后一个标“未尝试”。单个 CLI 最多等 30 分钟，超时就停下报告；Claude Code 安装包约 350MB，网络慢到 30 分钟装不完的，先在目标机上自己装好再同步。下载到的不是安装脚本（比如地域限制的网页）就停下报错。目标机的网络和代理是用户自己的环境，脚本不替用户配：注意经 SSH 登录的会话不会带上 WSL 自动注入的代理变量。
- `--目标家目录 <路径>` 把所有写入放到另一个家目录下，给测试用。
- 旧入口 `WSL/同步配置到WSL.py` 还能用：在 WSL 里跑，一跑就写，不做模型验证。和以前的差别：不再新建 `.codex/auth.json` 和 `.codex/magpie-desktop-models.json` 链接（已有的不动）；新增 Codex 的 `agents/` 链接；个人配置有 `~/.dispatch/config.toml` 时用 `~/.dispatch/`，否则用旧的 `~/.claude/派活配置/`；Codex 配置改成只动托管键、删掉 model_catalog_json；内容和链接指向没变的项不写；备份改放 `~/.dispatch-同步备份/`。

不做：不重启 WSL、不改 `.wslconfig`（有别的项目在 WSL 里部署，要重启先问用户）。重建 Orca 到 WSL 的连接，事先当作重启 WSL 征求用户同意（11-07 实测：断开那条 SSH 会话后发行版被整个重启了一次）。

## 用法一：Windows 主会话派 worker 到 WSL

Orca 通过 SSH 远程服务器 `<远程服务器名>`（地址见个人配置，免密钥口令）连进 WSL，在 Orca 的“远程 Orca 服务器”里能看到它。项目要先在 WSL 里 clone 一份放在 ext4 上（如 `~/work/<项目>`），再登记成 `<远程服务器名>` 上的项目：
```text
orca project setup-existing-folder --host <envId> --path /home/<WSL用户>/work/<项目>
```
登记后拿到 repoId。目前远程主机上起的是终端模式（Orca 1.4.251 回执写明）。三种写法：

- 新票、新工作区（远程不能用 current 和 new-child，用 new-top-level；基线由 `orca repo set-base-ref` 定好，一般不用 `--base-branch`）：
```text
orca orchestration worker-start --on <远程服务器名> --worktree new-top-level --repo id:<repoId> --name <短名> --spec-file <说明.md> --task-title "<标题>" --agent claude --model group/impl --effort <档位> --keep-open
```
- 同一张票返工：远程 worker 已完成时不能用 `send`，在原终端继续同一张票，`--worktree` 写原工作区的精确选择器：
```text
orca orchestration worker-start --on <远程服务器名> --worktree <原工作区精确选择器> --terminal <原终端句柄> --spec-file <说明.md>
```
  复用原终端时不能带 `--agent`、`--model`、`--effort`；原会话上下文还在，只用于同一张票的返工或补充，换下一张票就开新会话。用完执行 `orca orchestration worker-release --dispatch <id>`。
- 只读审查已有工作区：`--worktree "id:<repoId>::<该工作区的路径>"`，指向要审的那个工作区，不是主检出。

不要把 `--worktree` 指向主检出路径，那样 worker 会直接在主检出里改。三种写法由 实战项目下批首次使用时实测确认（Orca 1.4.251 帮助写明：远程不能用 current 和 new-child，新工作区用 new-top-level）。

- 依赖（`.venv`、`node_modules`）在 WSL 里单独装，不链接 Windows 检出里的。
- 看远程终端内容：`orca terminal read --environment <远程服务器名> --terminal <终端句柄>`。WSL worker 交回的交付文件路径在 WSL 里，用 `wsl -d <发行版> -- cat <路径>` 读（PowerShell 里直接用；Git Bash 会把 /home 改写成 Windows 路径，要在前面加 `MSYS_NO_PATHCONV=1`，11-07 实测）。
- 守护进程刚重启后，第一次远程派活可能报 “Timed out waiting for the remote Orca runtime”：先用 `worktree list` 确认没有半成品，再重试（实战项目批13 实测）。
- `agent_prompt_blocked`：按官方 orca-cli 指南处理（菜单出现时分开发 `--text` 和 `--enter`）。如果是 claude 首次运行的提示，回答后把对应的“已看过”键加进同步脚本。
- `hasSeenAutoDefaultNudge`：1.4.250 实测；官方 1.4.251 指南未提，已知提示是“要不要把 auto 设为默认权限模式”，同步脚本已处理。
- WSL 的资源和并发上限见个人配置。
- Windows 和 WSL 两份检出之间取分支、合并、取回 Windows，用 `脚本/WSL衔接.py`（先加 `--演练` 看要跑哪些命令）。

## 用法二：直接在 WSL 里开主会话

在 WSL 终端里 `cd ~/work/<项目>` 后运行 `claude` 或 `codex`。规则、agent、本手册都是同一份，原生子代理照常派。要让会话在 Windows 的 Orca 里看得到、管得到，不要在裸 WSL 终端里起，而是在 Orca 里打开 `<远程服务器名>` 上的这个项目，从 Orca 的终端里起 `claude`；Orca 的 worker 也只能从 Orca 里的会话派。切组合用 `组合与路由.md` 里的 WSL 命令。在 WSL 里开 Codex 主会话的，宿主差异见 `宿主差异.md`。
