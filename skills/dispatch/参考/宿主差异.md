# 宿主差异：Claude Code 和 Codex

需要：基础层。主会话是 Codex 时先读这篇；主会话是 Claude Code、又没写过 `config.toml` 的，可以跳过。

派活的规矩两边一样：拆活、定档、写规格、验收、改派都按手册来。不同的只有五处：技能和角色装在哪、怎么调用、模型和档位怎么传、只读怎么保证、怎么核对实际模型。下面逐条说，标了版本的是在那个版本上实测过的。

## 装在哪

| | Claude Code | Codex |
|---|---|---|
| 技能 | `~/.claude/skills/<技能>/` | `~/.agents/skills/<技能>/` |
| 角色 | `~/.claude/agents/<角色>.md` | `<Codex家>/agents/<角色>.toml`（`<Codex家>` 是 `CODEX_HOME`，没设就是 `~/.codex`） |
| 全局规则 | `~/.claude/CLAUDE.md`，片段见仓库 `CLAUDE.md片段.md` | `<Codex家>/AGENTS.md`，片段见仓库 `AGENTS.md片段.md` |
| 显式调用技能 | `/dispatch-retro` | `$dispatch-retro` |
| 会话记录 | `~/.claude/projects/<项目>/*.jsonl` | `<Codex家>/sessions/` |

两边的角色正文是同一份（仓库 `agents/*.md`）。安装器给 Codex 生成 toml 时只写 name、description、developer_instructions，在正文前加一段只读或限写的前言，不写模型和档位：Codex 里角色文件写了的模型会压过派发时传的值，写死就没法按配置调了。`dispatch-retro` 在 Codex 里设成只能显式调用，所以技能列表里看不到它是正常的。

手册里提到的脚本，都按本技能目录的相对路径跑，比如 `python <本技能目录>/脚本/体检.py`。Claude Code 下本技能目录是 `~/.claude/skills/dispatch`，Codex 下是 `~/.agents/skills/dispatch`。

## 先看生效配置

```text
python <本技能目录>/脚本/生效配置.py              # 当前目录所在项目
python <本技能目录>/脚本/生效配置.py --项目 <目录>
python <本技能目录>/脚本/生效配置.py --json        # 带来源和错误，给脚本用
```

它把个人配置 `~/.dispatch/config.toml` 和项目根的 `.dispatch.toml` 合起来（项目覆盖个人），列出每个角色的方式（native 原生子代理 / orca worker）、宿主、模型、档位，每项后面注明来自个人、项目还是未设置。不调用模型，随时可以跑。项目配置从 `--项目` 指定的目录（默认当前目录）往上找最近的一份，到含 `.git` 的那层为止。配置写错时它报出哪个文件哪一项、退出码为 2，派活前先改好；字段写法见仓库 `docs/安装与自定义.md` 第 4 节。

没有 `config.toml` 的老用户（只用 Claude Code、配置在 `~/.claude/派活配置/`）一切照旧：角色模型由 agent 文件和 magpie 路由组决定，手册第 1、2 节的路由组和别名规则照常适用。

## 派原生子代理

原生子代理只能是当前宿主的。生效配置里某角色写的是另一个宿主的原生子代理时，不能直接派：报告给用户，问是这次用当前宿主派，还是改走 Orca。不自动降级。

Codex 主会话（0.166 实测）：用 `spawn_agent`，`agent_type` 写角色名（explorer、reviewer 等），`model` 和 `reasoning_effort` 照生效配置传。实测子代理的会话记录里模型和档位就是传的值，角色前言也加载了。生效配置里该角色没写模型或档位，就不传那一项，子代理跟随主会话（贵，但不出错）。不写 `agent_type` 派出去的是没有角色说明的通用子代理，别这么派。

Claude Code 主会话：用 Agent 工具，`subagent_type` 写角色名。生效配置里该角色写了 model（只能是 opus、sonnet、haiku、fable 四个别名之一）就传；没写就不传，让 agent 文件里的 model 生效。要别的模型就走 Orca。档位：由调用方定档的具名角色（research、review、diagnose，组里可以带保底规则），调用时传 `effort` 生效，不传用角色文件里的默认档；review、diagnose 传 medium 会被保底规则抬到 high。钉死的角色传了不起作用。见手册第 4 节。

本机没有配置里写的模型时（派发报模型不存在），这一次退回个人配置里该角色的设置，没有就不传模型，并在给用户的回复里注明。

## 只读怎么保证

Claude Code 用 agent 文件里的 `disallowedTools` 真隔离：只读角色拿不到写文件的工具。

Codex 做不到这一点：角色文件不能改沙箱，子代理继承主会话的沙箱和审批设置。只读只能靠角色前言，加上主会话核对：
- 派只读角色（explorer、researcher、reviewer、diagnoser、verifier）前，在目标仓库跑一次 `git status --short` 记下来；子代理交回后再跑一次。
- 派 extractor、writer 时在任务里写明唯一允许写的路径；交回后核对改动只在那个路径。
- 多出别的改动就停下，把改动列给用户，不替子代理收拾。目标目录不是 git 仓库时没法这样核对，派之前告诉用户。

## 派 Orca worker

两边一样用 `orca orchestration worker-start`（见 `Orca.md`），`--agent` 决定 worker 是哪个宿主。实现者的宿主、模型、档位从生效配置的 `implementer` 取：
- 宿主是 codex：`--agent codex --model <裸模型名> --effort <档位>`。
- 宿主是 claude-code：`--agent claude --model <路由组名或别名> --effort <档位>`。

Codex 主会话派 Claude Code worker（或反过来）不需要额外设置，只是 `--agent` 不同。跨宿主只传规格、角色契约和相关配置，不传主会话上下文和认证。Codex 里能看到 Orca 自带的 `orca-cli` 和 `orchestration` 技能，第一次用前先跑 `orca skills get orchestration`。没装 Orca 时不派实现，主会话自己写。

## 核对实际模型

- Codex：打开子代理那次的会话文件（`<Codex家>/sessions/` 下最新的几个），看里面的 `model` 和 `reasoning_effort`。
- Claude Code：有 magpie 时用 `magpie usage --csv --last 1h` 按时间对；没有 magpie 时以 agent 文件和调用参数为准。

派活记录里的“宿主”“实际模型”两栏按这里核对的结果填。
